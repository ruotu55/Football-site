# Video — Play, Record, Render

Three ways a quiz becomes a video. All share the same in-browser flow; they differ in how frames are captured.

## 1. Play (in browser)
`video.js` `startVideoFlow()` → enables video mode on all levels → ball preloader intro (`.Storage/shared/ball-preloader-animation.js` `playBallPreloader`, GSAP merge→bounce→reveal) → `runVideoStep()` walks levels via `switchLevel()` (`levels.js`) with GSAP grid-overlay transitions (`transitions.js`). Each question: countdown → reveal (pitch/header flip in `pitch-render.js`) → reveal voice (`audio.js`). Pages are `html/{logo,landing,outro}.html`. Natural end fires `recording-naturally-finished` → `stopVideoFlow()`.

**Per-question countdown length** (runner 1 Regular): `QUESTION_COUNTDOWN_SECONDS` const at the top of `video.js` (currently **3s**, was 10s) drives `runVideoStep()`'s question branch — the timer circle drain, ticking, and colours (3=green/2=yellow/1=red+pulse) all derive from it. Applies to Play/Record/Render (one shared flow); the answer-reveal (voice + flip) is unchanged and runs after. Retune in one place. (`video.js` is imported with a `?v=` token in app.js / render-mode.js / render-segments.js — bump all three together on edit.)

## 2. Record (OBS)
`recording-flow.js` `startRecordingAndFullscreen(savedName, language)`:
1. **Preflight** (`recording-preflight.js` + shared `recording-preflight-core.js`): freeze each level's reveal phrase, collect logo/photo/voice/emoji URLs, **warm** them (preload). Team logo is a **hard gate** (`{critical:true}`) — if the crest can't load, recording is blocked (no "record anyway"). Non-critical misses warn only.
2. **OBS** (`obs-recorder.js`, obs-websocket-js v5 → `ws://localhost:4455`, no auth): `loadObsConfig(language)` from `/__obs-config`, create/refresh a Window/Screen Capture source, strip global audio inputs, `SetRecordDirectory` to `Ready videos/<Lang>/`, start. ~2.8s audio warmup before start if the capture source changed.
3. Run the play flow; on finish `stamp` the recording timestamp into the block.
- **Record-language chooser** (shared `record-language-chooser.js`): English / Spanish / Both. "Both" records EN then ES (`appState.doubleRecording`).
- **Mac split**: when `999_Mac_Uploader` runs, OBS record-dir + upload route to the Mac (localhost:9876).

## 3. Render (headless, frame-by-frame) — `render/`
Deterministic puppeteer + CDP virtual-clock render. Orchestrator `render/index.mjs`:
1. **PROBE** — `launchRenderPage()` (no capture), run the flow advancing virtual time frame by frame to count `totalFrames`, capture voice `durations` + audio `manifest`.
2. **CAPTURE** — spawn worker(s) (`worker.mjs`, default 1). Each re-runs the identical flow with the duration map injected, screenshots its frame window, pipes JPEGs into ffmpeg → segment MP4.
3. **CONCAT** — ffmpeg concat the segments → silent.mp4.
4. **AUDIO + MUX** — `audio-mux.mjs` + `audio-filtergraph.mjs` rebuild the soundtrack from the manifest (BGM crossfade + voice ducking) and mux onto the video.

**Intro voice timing (render):** the quiz-title (rules) voice starts **0.5s after the 4 balls appear** and the flow switches to Level 1 (first question) **only when that voice ends**. Mechanics: `video.js startVideoFlow` landing branch plays the ball preloader, then `setTimeout(introVoiceDelay)` → `playRules(...).then(() => switchLevel(2) …)`. `introVoiceDelay = LANDING_QUIZ_VOICE_DELAY_MS(500) + (render ? BALL_INTRO_RENDER_HOLD_MS(500) : 0)` — render adds the 0.5s background hold (ball-preloader `playBallMerge` HOLD) so the voice stays 0.5s after the *balls*, not the preloader (Play: 0.5s; render: 1.0s from preloader call). Like the ending voice, `playRules` resolves its clip via an async server resolver (`window.__resolveQuizTitleVoiceSrc`) — **pre-resolved + duration-prewarmed in `render-mode.js` setup** (real time, before the virtual clock) so it doesn't starve the clock and the start/switch land on time. (General render rule: any async clip/asset resolver on the live flow path must be pre-warmed in render setup, else it starves the virtual clock — see also the reveal voice `playFirstExistingClip` and the ending voice.)

**Render mode page side** (`render-mode.js`): URL `?render=1&lang=&script=&fps=60[&segment=]`. Seeds `Math.random` (mulberry32), exposes `window.__render` (`ready/done/start()/getDurations()`), `window.__renderDurations` (injected), `window.__renderScript` (live on-screen state, preferred over saved-by-name), `window.__audioManifest`. `start()` fires `_startFn` without awaiting; the driver advances the clock.

**Test clips** (`render-segments.js`): render just one segment — a slice of the SAME flow as the full render (shared video.js functions, same `render-mode.js` setup), stopped early via `window.__renderSegment` gates / `finishRenderSegment()`. **No loaded save needed** — clicking a clip (`app.js startRenderJob` with `segment` set) auto-picks the **first** recorded **block** (`pickTestSave()` → `GET /__recording-status`, first usable block — deterministic, no flaky random pick) and sends that block's frozen `block.script` as the `scriptObject` (so the headless page `applyScriptObject()`s it — the same proven path the full render uses). Output: `render-tests/<blockName> - <segment>.mp4`. **Do NOT use the legacy saved-scripts bucket (`/__runner-saved-scripts/lineups_regular`) — it is empty; the real saves are the 226 `recording-status.json` blocks.** (An earlier attempt sent only `script:<name>` with no `scriptObject`, relying on the headless `loadScriptByName` — that fails because blocks aren't in the saved-scripts bucket → render exit code 1.) Full renders still preview the current on-screen setup. Test clips are throwaway previews of the *flow*; which save they use doesn't matter. **All three runners go through the one shared `prepareRenderPlaybackUi()`**, which mirrors `startVideoFlow()`'s setup — including **`startBgMusic()`** (added 2026-06-08): test clips were rendering SILENT of background music while the full render had it, because `prepareRenderPlaybackUi` set up the playback UI but never started BGM. `startBgMusic` taps `__audioManifest`, so the BGM is reconstructed into the clip's muxed audio just like the full render. Keep any setup that `startVideoFlow` does (BGM, etc.) in `prepareRenderPlaybackUi` so it can't drift. Catalog is **exactly 3 clips** (`RENDER_TEST_SECTIONS`):

### ⚠️ CRITICAL render gotcha — "stuck at frame 1"
Under **paused virtual time**, `Page.captureScreenshot` **deadlocks** waiting for a compositor commit that never comes, as soon as a compositor-promoted animation (GSAP `force3D`/`willChange`, e.g. the ball-preloader `opening` clip) is running. The probe (no capture) is unaffected, so the symptom is: probe reports totalFrames, worker stalls at `captured=1`.
**Fix (applied):** launch with `--run-all-compositor-stages-before-draw --disable-new-content-rendering-timeout` (in `lib.mjs` args). Forces a frame commit per advance. `beginFrame` is NOT available in `headless:"new"`; `fromSurface:false` does not help. When mirroring render to sibling runners, copy these flags. (An x264 `malloc failed` seen mid-debug was just transient OOM from overlapping test Chromes, not a real bug.)

### Gotcha — render intro revealed a blank bg, the landing text popped in late
Two separate causes, both render-only:
1. **(Primary) `render-mode.css` hid the whole landing for the entire preloader.** The rule `body.render-mode-active.ball-preloader-active .landing-page { visibility:hidden }` kept the landing invisible the *whole* time the preloader was up — **including during the ball reveal**. So the radial mask opened onto a hidden landing (blank stage colour) and the text only "appeared" when the preloader hid and that class dropped. **Fix:** gate it on `:not(.revealing)` via `:has()` — `body.render-mode-active.ball-preloader-active:has(.ball-preloader:not(.revealing)) .landing-page`. Now the landing is hidden only during merge/bounce; once `.revealing` is added the mask exposes the real landing + text progressively, exactly like Play. **Same bug + same fix for the background effect (sun-rays):** `render-mode.css` also force-hides the bg-effect pseudo-layers (`body...ball-preloader-active::before`/`::after` = sun-rays + vignette) and forces a flat stage fill during the preloader (to avoid them compositing as a "smoky haze" behind the merging balls).
